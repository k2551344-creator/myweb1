# 회원 로그인·지점 결제 확장 적용 안내

## 구현한 내용

1. 이메일·비밀번호 로그인, 이름·이메일·전화번호 가입, 로그인 유지, 이메일 비밀번호 재설정.
2. 지점별 상호·대표자·사업장 주소·전화번호 관리와 회원 화면 하단 표시.
3. 지점별 토스 일반결제/자동결제 키 설정. 소유자만 저장하며 Secret Key와 빌링키는 서버에서 AES-GCM 암호화합니다.
4. 상품 상세·결제 약관·해지 안내 편집, 회원권과 같은 지점 락카 합산 결제, 약관 동의 기록.
5. 1회 결제 또는 주/개월 단위 자동결제. 1~36 범위에서 기간 수를 정합니다. 1주, 2주, 1개월, 3개월 등으로 설정할 수 있습니다. 1회 결제도 이용기간을 별도로 갖습니다.
6. 구매 당시 해지 문구를 표시하고 다음 결제를 중단하는 회원용 해지 기능. 락카 자동결제도 함께 종료합니다.

주/개월 주기는 상품마다 정합니다. 락카 가격은 월 환산이 아니라 **그 회원권의 한 결제 주기 이용료**입니다. 같은 락카에 설정한 5,000원은 1주 상품과 구매하면 1주당, 3개월 상품과 구매하면 3개월당 금액입니다. 상품 화면과 결제 전 합계에 이를 표시합니다.

구매 시 가격·주기·약관·해지 문구·락카 금액을 별도로 보관합니다. 관리자가 상품을 나중에 수정해도 기존 계약은 바뀌지 않습니다. 기존 계약의 계정을 보존하기 위해 토스 설정 변경 시 과거 설정을 삭제하지 않습니다.

## 적용 순서

### 1. DB 확장

Supabase SQL Editor에서 `supabase/setup/05_회원결제확장.sql` 전체를 실행합니다. 성공 결과는 `MEMBER_COMMERCE_READY`입니다. 기존 01번 최초 설치 SQL을 다시 실행하지 않습니다. 03번 저장 API가 설치된 프로젝트를 전제로 합니다.

기존 데모의 subscriptions/payments 테이블은 보존합니다. 이번 실제 결제 모듈의 주문은 gym_checkout_orders, 계약은 gym_memberships에 저장합니다. 기존 데이터의 자동 변환은 하지 않습니다. 기존 회원권이 있으면 중복 구매를 차단합니다.

### 2. 이메일 로그인·출석 설정 (계획 변경)

소셜 로그인은 사용하지 않습니다. 이미 실행한 05번은 그대로 두고 `07_이메일가입_전화번호출석.sql`을 추가 실행합니다. 06번 결제 스케줄 SQL은 로그인·출석 기능에 필요하지 않습니다.

정확한 이메일 발송 설정과 출석 기기 등록 방법은 [이메일가입_전화번호출석_적용안내.md](이메일가입_전화번호출석_적용안내.md)를 참고하세요.

### 3. 결제 서버 배포

GitHub Pages에서는 비밀 키를 사용하는 결제 승인을 실행할 수 없으므로 아래 Supabase Edge Function를 배포합니다.

- `supabase/functions/gym-payments/index.ts`

Supabase CLI를 사용하는 경우 center-manager에서:

```text
supabase functions deploy gym-payments --project-ref neswgimmvxzhqtnoaslu
```

`supabase/config.toml`을 함께 사용합니다. gym-payments는 함수 안에서 실제 사용자 JWT를 Supabase Auth로 검증하거나 스케줄러 전용 비밀값을 확인합니다. 키는 함수 소스에 넣지 않습니다.

Edge Functions의 Secrets 설정:

| 이름 | 값/용도 |
|---|---|
| APP_SITE_URL | https://k2551344-creator.github.io/myweb1/ |
| PAYMENT_ENCRYPTION_KEY | 안전한 난수 32바이트를 Base64로 인코딩한 값. 한 번 설정 후 반드시 안전하게 보관. 변경하면 기존 결제키를 복호화할 수 없습니다. |
| CRON_SECRET | 충분히 긴 무작위 비밀값. 아래 Vault 값과 같게 설정 |
| BILLING_SCHEDULER_READY | 처음에는 false. 아래 스케줄 검증 후 true |

SUPABASE_URL과 SUPABASE_SERVICE_ROLE_KEY는 Supabase 런타임 제공값을 사용합니다. 브라우저용 NEXT_PUBLIC 변수로 만들지 않습니다. 결제 키는 이후 Admin → 토스페이먼츠에서 지점별로 입력합니다. 일반결제와 자동결제의 Client/Secret 키 쌍을 구분하고, 처음에는 테스트 모드로 설정합니다.

### 4. 자동결제 실행 스케줄

1. Supabase Vault에 `gym_cron_secret` 이름으로 CRON_SECRET과 같은 값을 등록합니다.
2. `supabase/setup/06_자동결제스케줄.sql`을 실행합니다. 5분마다 만기 계약을 확인하며 월/주 경계는 한국 시간을 기준으로 계산합니다.
3. Edge Function Secrets의 BILLING_SCHEDULER_READY를 true로 바꾸고 Cron/함수 실행 결과를 확인합니다.
4. 테스트 구독으로 최초 결제·갱신·해지를 확인한 뒤 실결제를 켭니다.

Secret 값은 SQL 파일, 명령 인수, GitHub에 직접 적지 않습니다. [Supabase 스케줄 공식 문서](https://supabase.com/docs/guides/functions/schedule-functions)를 참고하세요.

### 5. 웹 반영

`npm run build:pages` 결과인 pages-dist의 index.html과 assets를 저장소 루트에 반영합니다. DB 05번과 서버 배포 후 main에 반영해야 기존 관리자 저장 기능도 새 API를 사용할 수 있습니다.

## 운영 동작과 제한

- 결제창에서 돌아왔다는 이유만으로 이용권을 발급하지 않습니다. 서버가 토스 승인 결과·금액·주문번호를 확인하고 주문을 완료합니다.
- 결제 요청은 15분 동안 락카/정원을 예약합니다. 승인 처리 중인 주문은 임의 해제하지 않습니다. 네트워크 장애 등 결과가 불확실하면 재확인으로 기존 토스 결제를 조회해 복구합니다.
- 카드 승인 거절은 결제 실패로 남습니다. 자동결제 실패 계약은 회원 화면에 센터 문의로 표시하며 임의로 연속 재청구하지 않습니다. 카드 변경·재가입 복구는 별도 후속 작업입니다.
- 구매 후 해지는 다음 결제를 중단하는 기능입니다. 중도 환불·부분 환불은 토스 관리자 처리와 DB 반영 확인이 별도로 필요하며 자동 환불/외부 취소 웹훅 동기화는 이번 범위에 포함하지 않았습니다.
- 결제 처리 중 해지 요청은 완료 후 다시 시도하도록 안내합니다.
- 회원정보의 전화는 연락용으로만 사용합니다. 카드번호·비밀번호는 저장하지 않습니다.
- 이름·전화번호와 계약 기록에 대한 회원 동의/센터 약관 본문은 센터에서 실제 내용을 입력합니다. 법적 효력을 보증하는 약관을 자동 생성하지 않았습니다.
- 기존 데모 출석 기능은 새 실결제 계약과 아직 연결되지 않았습니다.

토스 공식 문서: [자동결제](https://docs.tosspayments.com/guides/v2/billing/integration), [결제 API](https://docs.tosspayments.com/reference).

## 검증 범위

PostgreSQL 로컬 엔진에서 권한·가격 조작·동의·락카 예약·기간 계산·갱신·해지 등을 검증했습니다. 결제 서버 테스트는 토스 응답을 모의 처리합니다. 실제 카드 결제나 네이버/카카오/Google 계정 로그인은 계정 설정과 서버 배포 후 별도로 확인해야 합니다. 실제 서비스 키/DB 관리 권한이 없어 이 단계는 자동 적용하지 않았습니다.
