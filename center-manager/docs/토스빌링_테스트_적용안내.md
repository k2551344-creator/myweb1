# 체리복싱 카드 자동결제 테스트 적용 안내

작성: 2026-10-13. 이번 구현은 **테스트 전용**입니다. 계약 승인 후에도 live 키를 넣는 것만으로 운영 결제가 켜지지 않습니다. 별도의 운영 전환 검토가 필요합니다.

## 1. 분석 결과와 변경 범위

공개 웹은 React·TypeScript·Vite로 빌드해 GitHub Pages에서 제공합니다. Supabase Auth가 Google/기존 이메일 인증을, PostgreSQL이 회원·상품·구독·락카·출석 데이터를 관리합니다. 로컬 데모용 Next/SQLite 코드도 있지만 실제 공개 웹의 결제 서버는 Supabase Edge Function `gym-payments`입니다.

기존 SDK 카드등록, 서버 승인, 암호화 빌링키, 구매 당시 가격·약관 스냅샷, 해지 기능을 유지했습니다. 다음을 추가했습니다.

- 서버 환경변수에서 테스트 빌링 키 연결. 기존 테스트 일회성 키는 보존하고 기존 계약의 키는 별도 버전으로 유지
- 테스트 계정 허용 목록. 등록되지 않은 일반 회원의 테스트 결제 차단
- 주문별 3분 처리 잠금, 회차별 고유 주문, 동일 주문번호/멱등키로 재확인
- 일시 오류 재시도, 카드 거절 중단, 관리자 승인 조회(추가 청구 없음)
- 관리자 결제내역, 테스트 표시, 다음 결제일과 재시도 예정일
- Supabase Cron·Vault 설정 SQL

DB 초기화·기존 테이블 삭제는 하지 않습니다. 신규 SQL은 09번이며 10번은 예약 실행 설정입니다. 기존 1주·2주·1개월 및 그 밖의 설정 가능한 주기는 유지합니다. 갱신 금액은 구매 당시 서버 가격/락카 가격 스냅샷으로 계산하며, 이후 상품 가격 변경으로 기존 동의 금액을 임의 변경하지 않습니다.

## 2. 환경변수: Supabase → Edge Functions → Secrets

GitHub Pages나 Google Cloud가 아니라 **Supabase 서버**에 아래 값을 입력합니다. 공개 프런트엔드에는 시크릿 키를 넣지 않습니다.

| 이름 | 입력할 값 |
|---|---|
| `TOSS_ENVIRONMENT` | `test` 고정 |
| `TOSS_CLIENT_KEY` | 빌링 MID의 API 개별 연동 **테스트** 클라이언트 키(`test_ck_`로 시작) |
| `TOSS_SECRET_KEY` | 같은 MID·테스트 환경의 시크릿 키(`test_sk_`로 시작) |
| `TOSS_TEST_USER_IDS` | 테스트할 회원들의 Supabase Authentication → Users → User UID. 여러 명이면 쉼표로 구분. 이메일이 아님 |
| `APP_SITE_URL` | `https://k2551344-creator.github.io/myweb1/` |
| `PAYMENT_ENCRYPTION_KEY` | 무작위 32바이트를 Base64로 표현한 값. 기존 설정이 있으면 그대로 유지 |
| `CRON_SECRET` | 무작위 32자 이상 비밀값. Vault에도 같은 값 등록 |
| `BILLING_SCHEDULER_READY` | 처음 `false`, 아래 스케줄러 확인 후 `true` |

Supabase가 제공하는 `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY`를 사용합니다. `SUPABASE_` 접두어로 값을 별도 등록하지 않습니다. 사용자 요청의 JWT는 서버에서 `getUser()`로 검증하고, 주문 생성은 그 JWT로 RLS/RPC를 호출합니다. 예약 실행은 별도 CRON_SECRET으로 인증합니다.

암호화 키와 cron 비밀값은 암호학적 난수로 생성해야 합니다. 로컬 PowerShell에서 각각 아래 명령을 한 번 실행해 출력값을 직접 Secrets에 입력할 수 있습니다. 출력값을 채팅이나 GitHub에 올리지 마세요.

```powershell
node -e "process.stdout.write(require('node:crypto').randomBytes(32).toString('base64'))"
```

암호화 키를 분실/임의 변경하면 기존 빌링키와 결제 설정을 복호화할 수 없습니다. 안전한 곳에 보관하고, 기존 값은 덮어쓰지 마세요.

서버용 빈 템플릿은 `supabase/functions/.env.example`입니다. 로컬 사용 시 `.env.test.local`로 복사합니다. `.env*` 실값 파일은 Git에서 제외됩니다. GitHub에 커밋하는 것은 빈 예시뿐입니다. 웹 빌드에는 Supabase URL과 공개 키만 들어갑니다.

실제 회원과 완전히 분리하여 검증하려면 별도의 Supabase 테스트 프로젝트와 테스트 사이트를 사용하세요. 현재 서버도 test 키와 허용된 테스트 회원만 통과시키지만, 같은 DB에서 승인한 테스트 회원권은 출석 가능한 ACTIVE 회원권입니다. 실제 회원 계정은 테스트 허용 목록에 넣지 마세요.

## 3. DB와 서버 적용 순서

1. 05만 실행했다면 먼저 `supabase/setup/08_구글로그인_회원관리.sql`을 실행합니다. 08에는 전화번호 출석 확장이 포함됩니다. 기존 01을 다시 실행하거나 DB reset을 하지 않습니다.
2. SQL Editor에서 `supabase/setup/09_토스빌링_테스트.sql` 전체를 실행합니다. 결과는 `TEST_BILLING_READY`입니다. 추가 열·함수만 생성하며 반복 실행 가능합니다.
3. Edge Functions → Secrets에 위 값을 저장합니다.
4. `supabase/functions/gym-payments/index.ts`를 `gym-payments` 함수로 배포합니다. Dashboard 편집기를 이용한다면 기존 함수 소스를 이 파일 전체로 갱신합니다. **JWT gateway 검증은 꺼야 합니다.** 대신 함수가 회원 JWT 또는 CRON_SECRET을 직접 검증합니다. 이 설정은 `supabase/config.toml`의 `verify_jwt=false`와 같습니다.

CLI를 사용하는 경우 center-manager 폴더에서:

```powershell
npx supabase login
npx supabase functions deploy gym-payments --project-ref neswgimmvxzhqtnoaslu --no-verify-jwt
```

로컬 파일로 환경변수를 업로드할 때만 다음 명령을 사용합니다. 파일은 Git에서 제외되는 이름이어야 합니다.

```powershell
npx supabase secrets set --project-ref neswgimmvxzhqtnoaslu --env-file supabase/functions/.env.test.local
```

## 4. 서버 스케줄러 설정

1. Supabase Vault에서 다음 두 이름으로 secret을 만듭니다.
   - `gym_billing_function_url`: `https://neswgimmvxzhqtnoaslu.supabase.co/functions/v1/gym-payments`
   - `gym_billing_cron_secret`: Edge Functions의 `CRON_SECRET`과 정확히 같은 값
2. SQL Editor에서 `supabase/setup/10_토스빌링_스케줄러.sql`을 실행합니다. Cron과 pg_net 확장을 사용하며, 5분마다 `cherryboxing-test-billing` 작업을 실행합니다. 같은 이름으로 재실행하면 기존 작업을 갱신합니다.
3. 처음 `BILLING_SCHEDULER_READY=false`이면 HTTP 요청은 도착하되 비활성화 오류를 반환합니다. 함수 로그로 요청 도착을 확인한 후 Secrets에서 `true`로 변경합니다.
4. Cron 실행 기록과 Edge Function 응답이 성공하는지 확인합니다. **Cron SQL 성공은 HTTP 결제 처리 성공과 다릅니다.** Edge 로그와 관리자 결제내역도 함께 확인해야 합니다. 처리할 주문이 없으면 `results: []`가 정상입니다.

SQL은 pg_net 요청 큐에 잠시 저장되는 비밀 헤더를 일반 웹 역할이 읽지 못하도록 접근을 제한합니다. 권한/확장 설치 오류가 나면 그 상태로 멈추고 오류를 확인하세요. Vault secret이나 HTTP 헤더를 공개 출력하지 않습니다.

예약 실행 중단:

```sql
select cron.unschedule('cherryboxing-test-billing');
```

Secrets의 `BILLING_SCHEDULER_READY=false`도 설정하면 새 결제/자동 갱신을 차단합니다. 이미 승인된 주문의 관리자 조회·반영은 가능합니다.

## 5. 관리자 설정과 회원 테스트

1. 테스트 회원으로 Google 로그인 후 이름·전화번호를 저장합니다. Authentication → Users에서 해당 UID를 확인하여 `TOSS_TEST_USER_IDS`에 등록합니다.
2. 지점 소유자로 관리자 → 토스페이먼츠 → **서버 테스트 키로 빌링 연결**을 누릅니다. 새로운 구매에 테스트 빌링을 연결합니다. 기존 테스트 일회성 키와 구매 당시 계약 키는 보존합니다. 기존 live 설정은 이 버튼으로 덮어쓸 수 없습니다.
3. 상품 설정에서 정기결제와 `week/1`, `week/2`, `month/1`에 해당하는 주기·가격·약관을 저장합니다. 테스트 회원에게 이미 유효한 회원권이 있으면 기존 중복 회원권 방지 규칙에 따라 새 구매가 제한됩니다.
4. 테스트 회원이 상품 상세에서 금액·주기·해지 안내를 읽고 동의합니다. **카드 등록 및 구독 시작**을 누르면 SDK `requestBillingAuth()`가 실행됩니다.
5. 토스 테스트 카드등록 창에서 진행합니다. 실제 카드정보를 체리복싱 화면/채팅에 입력하지 않습니다. 토스 공식 안내에 따라 테스트 본인인증 화면이 나오면 인증번호 `000000`을 사용할 수 있습니다. 테스트 키 사용 시 실제 청구되지 않습니다.
6. 복귀한 서버는 회원과 customerKey(무작위 Supabase 사용자 UUID)를 대조하고 authKey로 billingKey를 발급합니다. billingKey는 AES-GCM 암호화 후 비공개 DB에 저장합니다. 카드번호·비밀번호는 자체 수집/저장하지 않습니다.
7. 첫 회차 금액은 서버 주문 스냅샷에서 읽습니다. 토스 승인 상태 DONE, 주문번호·금액·통화 일치 확인 후에만 회원권을 ACTIVE로 만듭니다.
8. 관리자 → **결제내역**에서 테스트 표시·승인 결과·다음 결제일을 확인합니다. 토스 개발자센터 테스트 결제내역과 주문번호·금액을 대조합니다.
9. 결과 화면을 새로고침해도 동일 주문이 다시 승인되지 않는지 확인합니다. 테스트 허용 목록 밖의 회원은 결제할 수 없어야 합니다.
10. 구독 해지 후 다음 결제가 생기지 않는지 확인합니다. 이미 처리 중인 결제는 결과 확인 후 해지해야 합니다. 카드 거절·잔액 부족 등은 토스 테스트 환경에서 재현 가능한 범위로 검사하고, 통신 장애·중복 동시 요청은 자동화 모의 검사로 검증합니다.

## 6. 자동결제·재시도 정책

- 한국시간 기준 계약 시작일을 기준으로 1주=7일, 2주=14일, 월 단위는 달력 월 계산입니다. 월말 날짜가 다음 달에 없어도 이후 월에 원래 기준일로 복귀합니다.
- 만료 시각 이후 5분 간격 스케줄러가 처리합니다. 카드 결제 주체는 토스 서버이며, 토스가 별도로 다음 달 결제를 예약해 주는 구조가 아닙니다.
- 각 구독/회차마다 DB 고유 주문 하나를 사용합니다. 요청 멱등키도 같은 주문번호이며, 재시도 전에 토스 주문조회로 기존 승인을 확인합니다.
- 통신 오류/일시적인 서버 오류는 최초 시도 후 5분·30분·2시간 대기 후 최대 3회 더 확인합니다. 실행 중 서버가 종료되면 3분 잠금 만료 후 다음 스케줄에서 회수합니다. 서버 장애로 재시도 기록 저장조차 안 된 경우에는 다음 스케줄에서 회수하므로 위 대기 간격과 다를 수 있습니다.
- 명확한 카드 거절은 FAILED로 기록하고 자동 재청구하지 않습니다. 갱신 실패는 회원권을 PAYMENT_FAILED로 표시하며 기간을 연장하지 않습니다.
- 네 번의 처리 시도 이후에도 불확실하거나 14일이 지난 주문은 자동 요청을 중단하고 관리자 확인 대상으로 남깁니다. 토스의 멱등키 유효기간(15일)을 넘어 자동 재승인하지 않습니다.
- 관리자 **승인 내역 조회**는 조회만 합니다. 이미 성공한 결제가 확인되면 회원권을 반영하지만 새 결제는 만들지 않습니다. 내역이 없으면 수동 확인 상태를 유지합니다. 토스 승인 없음/취소 완료를 확인하기 전 DB 상태를 임의로 초기화하지 마세요.
- authKey 발급 응답 유실처럼 빌링키를 안전하게 복구할 수 없는 경우 자동 재발급/새 주문으로 우회하지 않고 관리자 확인을 요구합니다. 카드 재등록·미결 주문 해제 자동 UI는 이번 범위에 포함하지 않았습니다.
- 장기간 장애로 신규 갱신 주문 생성이 24시간 넘게 늦어지면 과거 회차를 몰아서 청구하지 않고 RENEWAL_OVERDUE로 중단합니다. 최초 처리되지 않은 갱신 주문도 24시간 만료 시 중단합니다. 해당 계약은 관리자와 회원 확인 후 별도 처리해야 합니다.
- 해지/관리자 정지 이후에는 다음 회차 청구를 만들지 않습니다. 이미 처리 중인 주문의 결과가 불확실하면 먼저 정산 여부를 확인해야 합니다.

## 7. GitHub와 공개 배포

서버와 SQL이 준비되기 전에 새 웹을 올리면 결제 연결 오류가 나타날 수 있습니다. **09 SQL → 서버 Secrets/함수 → 10 스케줄러 → 웹 배포** 순서입니다. GitHub Pages 배포는 Supabase SQL·서버 함수를 자동 배포하지 않습니다.

`npm run build:pages` 결과인 pages-dist의 index.html, assets, .nojekyll, privacy.html, terms.html, legal.css를 저장소 루트로 복사한 뒤 main에 반영합니다. 시크릿·.env·node_modules는 제외합니다. 이번 개발 소스에는 서버와 테스트 코드도 들어 있지만 서버 키의 실제 값은 들어 있지 않습니다.

이 작업에서는 실제 테스트 키 입력, 원격 SQL 실행, Edge Function 배포, Cron 가동 및 실제 토스 카드 등록·승인을 수행하지 않았습니다. 자동화 검사는 모의 토스 응답과 로컬 PostgreSQL 엔진을 사용합니다.
