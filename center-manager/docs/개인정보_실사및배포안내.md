## 외부 서비스 실사

- Supabase: 실제 코드의 인증·DB·저장소·서버 연결. 고객을 위한 처리위탁 관계가 일반적이나 계약 당사자·프로젝트 지역·백업·지원 접근·재수탁자를 콘솔/계약으로 확인해야 합니다. 한국 리전 선택만으로 국외 접근이 없다고 단정할 수 없습니다.
- Google: Google에서 인증 결과·기본 프로필을 받아 Supabase를 거쳐 로그인. 단순 수탁자로 분류하지 않았습니다. 실제 OAuth 콘솔 범위·운영 전환·동의 화면을 확인해야 합니다.
- 토스페이먼츠: 표준 결제창·서버 승인·빌링 연동 코드 존재. 주문·금액·상품명·고객 식별자·결제키 등을 사용하며 현재 호출에 구매자 이름·전화·이메일을 명시적으로 전달하지 않습니다. 실결제 계약·라이브키·서버 배포·갱신 스케줄러 가동은 확인하지 않았습니다. 위탁/제공 관계는 실제 계약 기준으로 확정해야 합니다.
- GitHub Pages: 정적 웹 호스팅. GitHub는 보안 목적 방문 IP 기록을 안내합니다. 회원 DB 자체를 저장소에 올리는 구조는 아닙니다.
- 기존 이메일 로그인/복구 경로도 남아 있습니다. 실제 SMTP 업체 사용 시 해당 위탁·국외 이전 내역을 추가해야 합니다.

## GitHub Pages 적용 방법

현재 개발 브랜치에는 앞서 만든 Google 로그인·회원관리 변경도 들어 있으므로 이번 문서 추가와 함께 전체 브랜치를 main에 합치면 그 기능도 공개됩니다. 기존 기능 적용 준비와 DB 설정을 확인한 뒤 반영하세요. 이 작업만으로 main 배포나 Google 운영 전환이 완료되지는 않습니다.

1. 위 미확정 내용을 확정하고 web/legal 원본을 수정합니다.
2. center-manager 폴더에서 `npm run build:pages` 실행. pages-dist의 index.html, assets, .nojekyll, privacy.html, terms.html, legal.css를 저장소 최상위로 복사합니다. .env, node_modules, 전체 개발 폴더는 업로드하지 않습니다.
3. 검토한 변경을 commit/push하고 배포 브랜치(main)에 반영합니다. GitHub Settings → Pages에서 실제 배포 대상이 main / (root)인지 확인합니다. Actions 기반 설정이면 해당 배포 작업이 이 최상위 결과 또는 pages-dist를 게시하는지 확인합니다.
4. Actions의 Pages 배포 성공 후 아래 세 URL을 로그아웃한 모바일/브라우저로 확인합니다. 문서에 로그인·DB 연결은 필요하지 않습니다. 404면 배포 브랜치·루트 경로를 확인합니다.
5. 법적 문서만 먼저 게시하려면 privacy.html, terms.html, legal.css 세 파일을 main 루트에 추가할 수 있으나, 현행 홈페이지 하단 링크 추가는 그 홈페이지 소스에 별도로 반영해야 합니다. 최신 index/assets를 무작정 덮어쓰면 다른 개발 기능도 적용됩니다.
